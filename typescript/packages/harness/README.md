# @acyclic-labs/harness

TypeScript facade for the Rust-first Harness v2 runtime. It includes typed aggregate handles, reconnect/cursors, bounded hydration, an offline outbox, embedded/JSONL/WebSocket/HTTP-SSE/gRPC transports, explicit conversation selection, and native OpenAI-compatible model projection.

```sh
npm install @acyclic-labs/harness
```

Initialize Rust admission once with `const contracts = await NativeContracts.create()`. Build runtimes with `Harness.builder(contracts)`, compose owner-bound readers with `composeContentBindings(contracts, sources)`, and construct a `ParentProjectController(contracts, binding)`. Validate refs, attachment lists, and limits through `contracts.validate(kind, value)`; there are no separate TypeScript validation rules.

Use `HarnessBuilder` to register versioned tasks and tools and bind a model, context builder, policy, interaction handler, or replacement loop. Multiple task and tool revisions remain addressable by `name@revision`; an ambiguous unqualified lookup fails, and `selectModelTool(name, revision)` explicitly chooses the one schema exposed to the model. Executable handlers never cross the model boundary. `run(prompt)` is shorthand for the typed input API; the latter accepts ordered text and file parts. Canonical conversation messages carry only immutable `FileRef`s, while `selectModelContext` makes an explicit, revision-pinned model-facing selection. Its `ProjectableConversation` input carries the provider-authoritative `bigint` revision separately from the loaded messages, so compacted or partial remote views do not misstate history length. The reducer exposes `conversationPage(afterSequence, limit)` for bounded history reads; `conversation()` is a convenience that hydrates all pages while checking one stable revision. Use a page's `total_messages`, not its potentially larger `event_revision`, as the model-context revision. `composeContentBindings` routes by exact registered volume, including several owners on one provider; `verifiedContentResolver` adapts that owner-bound binding for model projection. OpenAI and Pi defaults share one bounded, grant-enforcing file projection boundary for text, native PNG/JPEG/GIF/WebP, and opaque references; unsupported content fails before a model request. The Pi bridge also accepts an explicit provider-specific projector. The OpenAI-compatible adapter accepts HTTPS endpoints or explicit loopback HTTP, with no URL credentials, query, or fragment.

`NativeContracts.create(wasm?)` provides an explicitly initialized Rust/WASM validator with exact TypeScript overloads for v2 files, messages, fork values, interactions, and task outcomes. It returns detached, deeply immutable Rust-admitted values, not the untrusted input object. `parseIdentity(kind, value)` brands agent, conversation, session, turn, task, operation, and effect IDs through Rust; `conversationMessageId(value)` does the same for message IDs. Conversation sequence numbers and other full-width `u64` positions remain `bigint`; bounded file lengths and limits become checked JavaScript numbers. Rust also owns `descriptorFor(bytes, mediaType)`, canonical action JSON encoding, and lossless event/history decoding; untrusted model JSON is parsed by Rust and rejected if an integer cannot be represented exactly as a JavaScript number. It also owns byte verification, typed attachment-manifest encoding/decoding, and report-to-seed fork conversion; `resourceRef(value)`, `extensionRecord(value)`, `forkSeed(report)`, `validateForkRequest(request)`, and `validateForkSeed(seed)` are async conveniences over native admission. Their public types retain volume class/owner and resource-kind relationships; generated WASM `any` values stay behind this typed boundary. `Harness.apply` returns an event with an honest unknown payload; `decodeEventPayload(event, parser)` establishes a type only after the commit result is known, so parser failures never obscure whether a command committed. Ref, attachment, and limits admission requires an initialized `NativeContracts` or `Harness` instance; no separate TypeScript validator remains.

`Harness.apply(command)` also returns `eventWire`, the generated v2 protobuf encoding of the Rust response event. Use it for exact native/WASM comparisons or transport; the projected `event.payload` remains `unknown` until explicitly decoded.

Use `HarnessBuilder.limits({ ... })` to narrow the shared v2 file, path, attachment, rendering, context, model-step, per-step event, and tool-call bounds; Rust/WASM validates canonical messages with those limits before admission and model projection. Grant root capabilities with `HarnessBuilder.grant(...)`; `scoped(ExecutionScope.create().onlyGrants(...))` may only retain a subset, including none. `ExecutionScope.withLimits({ maxSteps })` may narrow the model-step ceiling further for a child scope but cannot widen the builder's ceiling.

`run(prompt)` executes a live local turn even if a durable host is bound. Durable work uses `admit` with a stable operation ID and a versioned resumable task; host-backed contexts require recorded tool, interaction, timer, and child-admission boundaries.

For a local canonical conversation, create `MemoryConversation` for one agent, stage text and attachments with `stage`, and call `runConversation(runtime, operationId, contentRef, attachments)` or `runPrompt(runtime, prompt)`. Its `contentBindings()` can also be passed to `Harness.builder(contracts).content(...)`; grant only the owner's read/write capabilities needed by typed tasks and tools, which then use `TaskContext.readFile` and `stageFile`. Attached agents can receive read capabilities without receiving a writer. The host commits ref-only user history and an exact context selection before the model call, then publishes tool call/result artifacts and the assistant reply. More than 128 attachments use Rust's typed canonical manifest bytes, staged and verified before a ref-only event. This host is deliberately process-local: completed operations replay only while its in-memory output cache lives, and an interrupted model dispatch is reported as indeterminate rather than blindly retried. Use a durable host for restart recovery and resumable side effects.

`MemoryConversation.attachReadVolume(volume, owner.readBindings(delegatedScope))` mounts an attached owner's volume read-only. The owner issues a signed exact-file or private-directory grant with `delegateFileRead` or `delegateDirectoryRead`; its `readBindings` enforces that grant on every read. The receiving host checks returned bytes against the pinned digest. Without an owner-issued grant and authenticated reader, foreign refs are unreadable—knowing a path or ref is never itself authority.

The optional `@acyclic-labs/harness-objects` package binds an Objects bucket as the same `ContentBindings` reader/writer boundary. It stages exact versions with stable operation IDs, checks signed owner grants, and never adds an Objects dependency to Harness core.

Default context projection keeps every canonical attachment in storage while passing at most 1,022 attachment refs per message to a model, with an explicit omitted-count marker for the rest. Providers may replace this projection policy without rewriting conversation history.

`HarnessClient` and `ProjectionStore` cover transport and UI projections. Offline-safe commands accept only typed file references and routing metadata; outboxes pin one validated clone and reject inline bodies, bearer scopes, and extra command or authority fields at runtime. In-memory outbox/cursor stores are process-local; use a persistent host for restart recovery. The wire contract is `acyclic.harness.v2`, with no v1 dual-read or migration; a pre-v2 IndexedDB outbox remains untouched but cannot be opened by v2. A future alone is not a durable task.

`ParentProjectController` exposes project fork, merge inspection, Filesystem application, and verified receipt publication through a provider-owned parent binding. The provider authenticates the parent scope on every operation; the facade returns only opaque, controller-owned merge handles and pins the inspected target generation. After a successful join, `publishProjectMergeReceipt(plan, receipt)` requires that handle, the exact source/target generations, a typed `ProjectMergeReceipt` with a validated 16-byte Filesystem operation identity, a bounded provider-owned proof tied to the target Filesystem provider, and a `ProjectMergeNotice` whose payload is only file refs; the owning host verifies the proof against durable Filesystem state and atomically appends receipt plus notice to the parent Stream. A child can report changes but cannot publish them into its parent through this API. Fork seeds pin an inclusive inherited-message prefix and the exact clean child-private Filesystem generation, may attach additional reader agents, and carry parent-approved exact-file read grants for references from controlled private, project, and shared volumes; manifest-backed attachment members identify their published list and are checked by the owning provider. Child-owned inherited-context files are also readable by the child and attached agents through exact-file grants. The async `forkReadableReferences` returns the pinned access plan, never a bearer token. Omitted history is not implicitly shared. Foreign private owners must mediate their own bytes. Only the original volume owner writes there. The child conversation still has one owning agent. Conversation history, private volumes, and context never merge implicitly.

Private-directory sharing does not require a fork. `delegatePrivateDirectoryRead` issues a signed reader-bound, segment-bounded capability from the original owner's scope; `directoryReadCapability` computes that same canonical boundary. Storage adapters resolve it lazily at the owner's current generation, and attached agents cannot use it for writes or internal storage paths.

Durable interaction tickets and resolutions are typed, ref-only values. `interactionTicket` and `interactionResolution` admit their envelopes through Rust; the Rust Stream admission path verifies staged request/answer/decision bytes, the exact responder grant, and compare-and-set versions. `TaskContext.interactTyped(questionOrForm, pinnedSchema)` advertises that JSON Schema, validates a returned answer through Rust, then applies its typed parser; non-answer outcomes remain distinct. Approvals bind an operation ID and action digest. Decline, cancellation, expiry, denial, and indeterminate reconciliation remain distinct outcomes. Hosted task contexts require stable operation IDs and a durable host route for interactions and tools; process-local `InteractionHandler` callbacks apply only to live local tasks.

Task requirements use exact bindings such as `task:extract@2` and `tool:search@1`, or a named boundary (`model`, `context`, `interactions`, `policy`, `host`). Build-time validation rejects missing versions and task dependency cycles.

Task code may invoke a registered descendant only with an exact `task:spawn:<name>@<revision>` grant in its effective scope. `TaskContext.task(definition)` returns an opaque typed `TaskRef`, not the child implementation; use that ref with `context.spawn`, `context.admit`, or a context-created task group. The group checks the same grant on batch admission and reconciliation. Scope narrowing can remove individual descendant grants without unregistering the owner's definitions, and self-recursion requires its own explicit grant. Owner-level `AgentHarness` operations remain under the trusted caller's control.

Every tool call requires an explicit `tool:call:<name>` grant, narrowed through child scopes before policy evaluation. A replaceable policy exposes `identity()` with a name, version, and nonzero 32-byte implementation digest (construct it with `policyIdentity`); a durable host reports its enforced identity through `policyIdentity()`. Build and dispatch reject mismatches, including an added scoped policy that the host has not pinned. Scoped policies retain separate, independently approved action decisions. Local approvals carry a Rust-computed canonical action digest and stable operation binding; only an `approved` response permits dispatch. Durable calls always delegate the decision and exact-action approval to the owner host, never the local handler.

There is no implicit built-in tool set: register each versioned tool and its executor explicitly. `defineTool` requires JSON input/output schemas plus typed parsers; the builder admits every pinned task and tool schema through Rust's strict canonical JSON contract, and Rust validates each invocation and result before the parsers admit values to handlers or callers. Model-visible definitions contain schemas only, never handlers. `TaskDefinition.live` runs in the local process via `spawn`; it is not durable. `TaskDefinition.resumable` requires input/output schemas and a typed checkpoint-state schema created with `defineRuntimeSchema(id, nonVacuousJsonSchema, parser)`, an explicit 32-byte implementation digest, a durable host, and async `admit(definition, input, operationId)`; retry an indeterminate admission with the same stable operation ID. A restored state is checked against its JSON Schema and parsed before entering a typed transition. The host owns idempotency, checkpoints, waits, effect reconciliation, and replay. Recovery interfaces return unknown output, never a caller-selected type; the exact pinned definition and Rust JSON Schema check plus typed parser establish the result type. A pending host task keeps `result()` pending; `indeterminate` means a genuinely unresolved terminal outcome. Live `TaskContext.call` returns the typed value; an admitted task uses `callDurable(operationId, tool, input)`, whose typed outcome preserves success, failure, cancellation, or indeterminate reconciliation without retrying an uncertain effect. A durable policy decision requiring approval is handled by the host's exact-action interaction journal; the TS facade does not self-approve or short-circuit that host boundary. `reconcileEffect(effectId)` returns Rust's ref-valued `EffectStatus`, never a caller-invented result type; a successful result must be resolved through the owning content provider. The local runner intentionally refuses to execute resumable transitions, because looping over them in memory cannot provide those guarantees. For retryable batches, pass a stable group ID to `group(policy, id)`, reuse the batch ID, and provide the exact task definition to `reconcileBatch(definition, batch)` through the host's recovery binding. Host-backed task handles expose authoritative event streams and cancellation through `Task.fromHost`, and reattachment checks the pinned task implementation digest and result schema.

Registered `TaskRef` and `ToolRef` values are opaque handles: task code cannot access the child's implementation, tool executor, or inline handler. `TaskContext` and `TaskGroup` keep the raw Harness/content binding private, so file reads remain subject to owner-mediated resolution and scope grants. Direct local approval rejection throws a typed `ToolApprovalError` with its exact outcome and operation identity.

Durable batch replay binds the entire ordered input list by a Rust-canonical digest, not merely its batch ID; the host must return that pinned digest with contiguous entries. Host-backed task drivers also provide the persisted terminal event (stable ID and sequence) so a truncated event stream can recover its actual outcome without inventing a cursor position. `MemoryConversation` is deliberately volatile: after an uncertain model dispatch it never blindly regenerates. It can resume publication from an in-process completed output, or its owner can explicitly call `abandonIndeterminateTurn(operationId)` to record a ref-only system notice and continue with a new turn. For crash-safe model-step reconciliation, use the Rust execution journal and `ModelProvider.reconcile` through a durable host.

Durable mailbox messages carry a validated `FileRef`, not inline payload bytes. Store and authorize the referenced file before sending; the host owns residency and recipient access checks.

When a conversation references files from several owners, bind their authenticated readers with `composeContentBindings(contracts, [{ volume, content }, ...])`. Routing uses the exact volume and owner identity carried by each `FileRef`, so distinct agents on one provider can be mounted together. A single owner-bound writer may be included. The composition never makes a reference itself an access grant.
