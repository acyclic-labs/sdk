# Approval map (2026-10-17)

Survey base: origin/main 1b26e4a77. No implementation changes preceded this map.

| Layer | Existing machinery | Gap to the requested contract |
| --- | --- | --- |
| Task files | `harness/src/task_volume/schema.rs` defines immutable `ApprovalRequest`, `ApprovalDecision { request, principal }`, canonical `approvals/<id>/request.json` and `decisions/<principal>.json`, and `Owner::Approver`. `query.rs` supplies approval selectors; snapshots and cursor follow already exist. | These paths are schema/query support, not the execution authority. `TaskFiles::write` rejects Approver/Harness files. There is no authenticated decision-file writer or approval payload contract. |
| Interaction host | `filesystem/interaction_host/{content,publication,resolution}.rs` stages requests and answers, verifies exact responder capabilities and signed scopes, and resolves versioned conversation interactions. `ApprovalBinding` pins operation and action digest. | Content lives at `.system/interactions/<id>/...`, with authoritative conversation reducer actions. Requests contain prompt and digest, not the complete operation arguments. Client file writes cannot settle this path. |
| Journal | `filesystem/execution_journal/interactions.rs` opens idempotently, rejects changed requests, checks execution ownership and compares terminal answers on retry. | Approval settlement duplicates the host resolver: answer staging, outcome conversion and version handling. Decisions are answer files keyed by version/operation, not authenticated principal task files. |
| Dispatch | `executor/{tool_execution,tool_resolution}.rs` evaluates ToolPolicy and opens/waits for an interaction on RequireApproval. `runtime/tool_dispatch.rs` independently evaluates policy for native dispatch. `runtime/tools.rs` shares the digest binding and terminal-outcome check. | Both ToolPolicyDecision::Allow and no policy bypass approval files entirely; Deny also leaves no decision file. Policy is an optional trait object pinned by identity, not a resolved settings file. |
| Recovery | `filesystem/task_runtime/interactions.rs` reconstructs the exact tool/policy binding, checks recorded interaction readiness, and inspects model history before resuming. Existing task leases and journal claims fence dispatch. | Recovery follows the interaction ledger, not approval file queries. File decision admission must join existing execution fences; an independent in-memory approval store would break recovery. Cancellation must settle pending files too. |
| Hooks | `hooks/output.rs` parses pre-tool approval requests, shared decision reasons, argument replacement and blocking output. | Hook ask is another input to the same approval gate; it must not create a second settlement mechanism. |
| Clients | Approval query fixtures exist under `tests/scenarios/task-query`; harness-tui has prompt navigation flags for approval/question items. GraphCoder parity data describes always-approve release behavior. | No approval widget or composable always/never/rules/llm/parent/human data policy was found. `NeedsApproval` restoration is in open gc-client PR #828 (head 751a5cb9d6fa6a09a59734e43ee1a103cc459250), not on this main. |

Next slices: reuse task-file publication, authenticated scopes, live queries and existing journal claims; add the exact request/decision contract and fenced execution with a real-path Loom model plus negative control. Then add approver kinds and composition with property/fuzz coverage and scripted data scenarios, followed by the TUI. GraphCoder must receive always through config; remove permissive bypasses when the common gate is wired. No production auto-approver implementation or GraphCoder-specific Allow branch was found; the current shortcut is optional policy / Allow dispatch itself.
