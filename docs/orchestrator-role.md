# Orchestrators and questions

Orchestrators are the root and user-facing role and can spawn orchestrators. Shipped roles inherit the session model. A model configured in a role's `AGENT.md` overrides the inherited model and explicit spawn selections. Fixed-provider embeddings must serve that model or use `LocalHarnessConfig::resolving` to resolve it.

`--topology single` selects one coding root with no spawn, send, archive or wait tools and no delegation instructions. Spawn-capable roles share the atomic, parallel fork, speculative fork and sequence decision procedure. Every mode prioritizes correctness, then completion time; cost is not a goal.

Only the orchestrator role grants the question plugin. The plugin owns the ask declaration, input-fence recognition and attention policy. TUI, web and IDE hosts select it when starting a session with a user surface; non-interactive hosts leave it disabled. CLI --questions=true/false overrides selection. Browser session options user_surface and questions provide the same start-time choice. Later attachment never changes a session's toolset. Ordinary messages remain available.

The user directed deletion of hierarchical question routing, triager/explanation roles, authored relay queues, learned attention signals and escalation policy. A child communicates ambiguity through its ordinary result or send. Orchestrators decide or ask directly; the question surface identifies the asking agent. Approvals and their parent chain remain independent and unchanged.

Human views prioritize orchestrators through the existing paged explorer and immutable role selections. Contributor branches begin collapsed. Expand their orchestrator to inspect workers, advisors and reviewers; ordinary input keeps the closest orchestrator as its default target. Search still reaches contributors.

Headless orchestrators decide within their authority and report assumptions in their final result. Manual approval on closed input retains the existing declined-tool result and continues the model loop. The question plugin does not change approval policy, LLM approvers or the approval chain.

Each session root records its question-plugin choice independently of the serving workspace. The ask tool accepts only canonical private ui/ paths and uses the existing Write hook aliases. Role-filtered explorer paging advances the underlying window even when every row in a window is collapsed.
