# Filesystem adapter

Enabled by the `filesystem` feature (`filesystem-local` adds the durable local stores).

Stock execution enables `CompactionPolicy::default()` with a 16,384-token
response reserve and 20,000-token recent suffix. The selected `ModelProvider`
supplies its actual capacity and digest-bound additive token counts; unsupported
accounting is an explicit error before model dispatch. `LocalHarness::with_limits`
and `with_tools` take an explicit `CompactionPolicy`, while `new` uses the default.
`HarnessBuilder::compaction` and `FilesystemTaskExecution::with_compaction_policy`
install the same configuration. The stock task command host's `with_model` binds
the model, provider, context pipeline and policy together. `Disabled` leaves the
installed context pipeline in control; replacement thresholds preserve task
accounting, ownership and exact journal recovery.

Explicit bridge from Harness resource references to versioned Filesystem workspaces. It keeps generation identities visible rather than pretending mutable paths are durable references.

The local preset's file tools require both their tool-call grant and the caller's exact volume read or write grant, including on completed replay. Its ephemeral directory-listing tool retains the first page observed for each operation ID, so reconciliation cannot silently return a newer generation.

Choose an `acyclic-fs` authority and object store for the required durability boundary, then wire the adapter into Harness. See the [adapter API](https://docs.rs/acyclic-harness/latest/acyclic_harness/filesystem/), [Filesystem guide](https://docs.rs/acyclic-fs/latest/acyclic_fs/), and [Harness guide](https://docs.rs/acyclic-harness/latest/acyclic_harness/).

For an infrastructure-free local run, `LocalHarness::new(model, provider).await` creates a fresh agent, its private volume and bound conversation, and a runnable stock loop. `local.run(prompt)` is the short text path; stage a file through `local.storage().stage(...)` and pass its `Attachment` to `local.run_with_attachments(prompt, attachments)` for the same canonical ref-only path. `local.storage()` and `local.bundle()` expose the full typed conversation API. `LocalHarness::with_limits` accepts an explicit agent identity and checked limits. The default registry contains `acyclic.list_files` for bounded, generation-pinned lazy discovery, `acyclic.read_file` for authorized immutable UTF-8 content, `acyclic.edit_file` for an exact UTF-8 replacement at a pinned generation, and `acyclic.write_file` for bounded UTF-8 text in the agent-private volume with a pinned `FileRef` result. The write tool uses its operation ID as a single-file upload retry identity, so reconciliation checks the provider's atomic receipt before any write. The portable tools use the admitted task's original reader and publisher; providers without operation-bound publication report Unsupported. General `TaskContext::stage_file` retains multi-path staging, while `stage_file_once` binds one publication to the operation. These tools have no shell or parent project merge authority. `LocalHarness::with_tools` replaces that registry and requires explicit grants for the supplied tools. This preset is deliberately ephemeral; substitute durable providers for resumable deployments.

For customized local composition, `MemoryHarnessStorage::new(agent, file_limit).await` creates the agent-private volume, bound conversation, Stream journal, and exact content verifier. `storage.builder()` starts a `HarnessBuilder` with that journal and an owner-bound content publisher; `storage.default_tools(limits)` provides the same portable read/write/edit registry and owner-bound directory tool for custom builders without reconstructing it. The caller selects its model or custom executor and grants. Typed tasks and tools can call `TaskContext::stage_file` and `read_file` under their narrowed grants. `storage.stage` uploads primary text or an attachment before admission and returns its pinned `FileRef`; `storage.run_conversation` appends the canonical user record, commits and verifies an exact model-context selection, executes the typed turn, and appends the assistant result as ref-only history. `storage.run_prompt` is the text convenience over that path. Retry by operation ID recovers the same selection even if later turns exist.

Harness volumes have three distinct lifecycles: project workspaces fork from an exact generation and merge only through an inspected Filesystem join; agent-private workspaces are created afresh for each agent and never merge; session-shared workspaces are read through explicit grants. The default `ParentProjectController` binds the parent conversation reducer, verifies the acting scope belongs to its immutable agent, and selects its exact project volume. Only that parent's scope can fork (`fork:publish` plus project read), prepare promotion, or publish the inspected `ParentMergePlan` (`project:merge` plus project write). The raw Filesystem `JoinPlan` is not returned; conflict inspection, selected-side resolution, driver resolution, and expected-generation CAS publication all remain on the parent controller. Children may report their changes, but cannot authorize a merge into the parent project. A `FileRef` carries a generation-pinned path, SHA-256 digest, byte length, media type, and display name, but does not grant access. `ContentGrant` verifies the caller's signed scope for one exact volume operation.

`FilesystemProjectWorkspaces` adapts that controller to Harness's provider-neutral `ProjectWorkspaceProvider` binding. An inspected join plan retains the original parent authority and Filesystem CAS heads, accepts only its signed scope on application, and returns a typed outcome; opaque conflict keys preserve native name bytes for exact selected-side resolution. Publication of its successful `ProjectMergeReceipt` and conversation notice remains a separate parent Stream operation.

`FilesystemForkPreparer` is the parent-controlled, retryable path from an exact `ForkRequest` to a ref-only `ForkReport`. The request fixes child volume identities and inherited-context bounds before work begins. A separate provider-owned journal claims the entire request under its operation ID and stores the final report, so `reconcile` reads durable state without starting a second fork. Provider-global allocation claims prevent another preparation, even under a different parent, from adopting either child volume; an exact seed digest binds each allocation before `FilesystemForkVerifier` permits publication. Custom parent-controlled preparation paths must call `FilesystemHost::claim_fork_seed` with the exact parent reducer and authenticated parent scope; it compares inherited bytes with the selected parent prefix before claiming volumes. Project and child-private work use distinct operation-derived Filesystem retry keys; a changed request under the same ID conflicts. The adapter captures the bound Stream parent revision and Filesystem project/shared selections. Other selected provider resources are reported as unsupported until their capture adapter is installed; an unavailable required capture cannot be published. These journals are not stored in the child private or project volume, preserving their publication and merge invariants. This preparer does not claim a common Stream/Filesystem boundary or accept an attestation it cannot verify.

Install other exact resource owners with `with_capture_provider`. The preparer journals each capture start and result. Once started, another attempt calls the provider's `reconcile` method by the stable fork operation ID and never blindly repeats `capture`; an unresolved observation remains explicitly indeterminate rather than committing a misleading report. Read-only Machines and Objects captures can safely re-read their immutable revision. Publication still requires the corresponding provider verifier.

An owner can share one pinned private file or a segment-bounded private directory with an unrelated attached agent, without inventing fork lineage. A reader-bound `FilesystemContentVerifier` exposes `list_private_directory` and `read_private_path` through that signed, read-only scope, so durable adapters can open the owner's workspace lazily without mounting or copying it; pagination and subsequent reads can require the same observed generation, so a changing head yields a conflict instead of a mixed view. Staged files carry an atomic, versioned metadata index so a discovered path retains its actual media type, display name, and digest rather than being guessed from its name. Internal upload receipts and metadata are excluded from delegated discovery and cannot be read or overwritten through agent file APIs. The local `MemoryHarnessStorage` exposes the same owner-issued delegation and lazy list/read flow.

Use `put_content` to stage message text and attachments before appending a conversation event. Bind `FilesystemContentVerifier` to the Stream aggregate so admission checks every exact file version and refuses dangling references. Large ordered attachment lists can be staged with `put_attachment_manifest`; admission resolves the complete manifest, validates its count and canonical JSON, and verifies each member. The parent controller's `materialize_inherited_conversation` writes the selected bounded prefix into a reserved path of an empty child-private generation and returns exact read grants and attachment manifests for every child/attached reader; ordinary agent uploads cannot write there. Its canonical bytes bind both the authoritative parent messages and the attached-reader set, so changing either under the same staging key fails. The `ForkSeed` pins that private generation, and `FilesystemForkVerifier` checks that no file or directory outside the selected prefix was adopted before the fork event becomes visible. After a successful inspected join, use `merge_receipt` and bind `FilesystemProjectMergeVerifier` to the parent Stream aggregate: publication verifies the provider-owned join witness against the durable operation fingerprint, exact source/target generations, retry identity, and join ancestry, then appends the project-merge receipt and parent conversation notice atomically. The notice may be published after later project edits because it names immutable generations. No private volume or child history is merged.

The raw Filesystem host and the `AuthorityIssuer`/verifier pair are trusted provider wiring, not reader inputs. Resolve an attached agent's signed scope against the owner's retained verifier; accepting a reader-supplied verifier would let that reader invent its own grants. The ref and its volume identity remain non-bearer even when the owner makes a directory lazily discoverable.

`FilesystemExecutionJournal` keeps model observations and tool inputs/results in pinned agent-private files. `FilesystemInteractionHost` stages interaction prompts, answers, and optional approval explanations there, then commits ref-only records to the owning conversation Stream aggregate. The executor journal delegates interactions to that same aggregate; it has no second interaction history. Resolution requires an authenticated grant for the exact interaction plus `interaction:resolve`, validates staged bytes against the original request, and reconciles identical retries.

Execution replay uses `replay(operation_id, after, maximum)`: `after` is the exclusive one-based record sequence, zero starts at the first record, and `maximum` is a caller-selected positive `u32` allowance. Providers can return shorter internal batches. Empty pages end replay. `ExecutionReplay` supplies shared sequence and identity validation across pages without retaining pages. The stock executor uses it and keeps only the current step or tool call; custom executors can use the same cursor when resuming. Staged execution payload identities include their exact content digest, so an unpublished file cannot block reconciliation with different bytes at the same logical event position; the journal append remains authoritative.

`FilesystemWorkflowJournal` applies the same rule to resumable state-machine transitions: checkpoint state and input live in descriptor-verified private files, while its Stream contains only exact `FileRef` records. Emitted `WorkflowCommand`s contain stable operation IDs, kinds, and immutable argument refs—not inline command bodies. The journal verifies each command payload's owner-private residency before commit and on public replay. Normal commits reuse a verified in-process checkpoint/identity summary; cold recovery and uncertain appends rescan authoritative record envelopes before proceeding. Workflow lifetime and identity counts have no fixed ceilings. Caller-selected task/session budgets and payload limits remain authoritative; lazy bounded identity projections remain an open recovery gate. A lost append acknowledgement is reconciled by operation identity instead of blindly dispatching the transition again.

`FilesystemSchedulerPayloadStore` stages join, quorum, and reducer JSON results in an explicitly granted agent-private volume. The coordinator verifies each exact staged result and its declared schema before publishing its `FileRef`, and repeats that verification on replay.

For a scheduler-owned task workflow, obtain `CoordinatorTaskHost::journal_owner(task_id, fence).await` from an `Arc` of the host, then use `FilesystemWorkflowJournal::for_task` with that binding. The binding's `workflow_admission()` supplies the initial checkpoint and request digest derived from the retained task admission and registered machine. The constructor uses the coordinator's own Stream provider and fixes the journal path to the task ID. Admission and transition publications atomically compare both the coordinator revision and journal tail; cancellation or a lease change between validation and publication prevents the write. Checkpoint retries also require the current uncancelled lease, and records must reproduce the pinned machine transition. Private payload staging precedes this transaction and can leave unused files after a conflict. Generic command dispatch and persistent composition remain required; this constructor alone is not a complete persistent task runner.

`FilesystemExecutionJournal::for_task` binds one execution operation to the same task owner and provider. Starts require the current uncancelled lease; model starts also require the exact retained shared-budget claim. Observations and tool settlements require their prior start and the retained execution fence, including during cancellation or reconciliation. Publications compare coordinator and execution tails in one Stream transaction. Cold append rebuilds a compact, bounded retry/start index from pages; warm append reads only the newly committed suffix. Replay verifies model starts against retained claims without charging again. A task authority has no conversation interaction owner and returns `Unsupported` for interaction calls; a conversation authority continues to use its existing interaction ledger. The binding can be reopened for settlement after cancellation, but that does not permit fresh starts or workflow writes.

Pass a task-bound workflow journal to `AgentHarness::open_task(task_id, &definition, fence, journal).await` to recover a registered resumable task. The same path is available through `TaskContext::open_resumable_task` and `TaskDefinition::open`. It verifies the registered definition and the retained input, schemas and scope before opening the existing workflow host. `ResumableTaskSession::step` validates completed values against the admitted output schema and checks uncancelled ownership even for cached exact retries. `latest_transition` reads the latest committed status and outbox without retaining historical bodies; opening an existing checkpoint after cancellation is permitted for recovery, but advancing it is rejected. This session does not dispatch commands or settle scheduler outcomes, and live futures have no durable checkpoint.

Configure shared ceilings with `CoordinatorTaskHost::with_session_limits` before sharing the host. New roots then publish their declaration and immutable session configuration in a single atomic coordinator append, so another worker cannot claim an unconfigured root between two writes. Children inherit the retained root budget. Reopened hosts must select the same ceilings; observation rejects a changed or missing configuration. The lower-level `DistributedCoordinator::declare_session` provides the same owner-authenticated atomic publication. Workflow suspension adds lifecycle events and optional workflow metadata; older serialized operation states default that metadata to absent. Machine-owned sandbox checkpoints remain separate.

`FilesystemTaskRuntime::open` optionally composes caller-owned Filesystem and Stream providers, the existing task/machine/tool registries, a private volume, signed owner scope and shared session ceilings. Create or reopen the volume first; the selected providers determine persistence. `harness()` exposes the existing typed runtime and `workflow_journal(task, fence)` supplies its task-bound workflow journal. `stock_execution(task, fence, turn, model, provider, context)` returns a stock executor with mandatory shared accounting and its bound execution journal. Use its task-namespaced `operation_id()` in `TurnInput`; `execute` accepts no replacement journal or accounting host. The task's admitted limits and tool grants apply, and input files must satisfy the task's retained read grants even when the storage owner can read them. The existing task host remains accessible through `task_host()`.

The mutable `DistributedCoordinator` now keeps at most 64 complete retry intents. Its `open`/`refresh` path builds missing immutable retry locations under `harness/v3/coordinator/intent-locations/`, pointing to the existing coordinator revision, canonical event digest and source commit ID. This requires write access to that derived namespace during bootstrap or repair. A location is verified against the authoritative event on a cache miss; the location contains no task state, budget decision or second command ledger. Root/session retries retain their original single-envelope check even after cache eviction. Projection publication failures do not append another semantic coordinator event; a later refresh can finish missing index publication. Read-only event consumers can use `read_coordinator_event_page`, which does not create these locations. Invalid or extended index records fail closed; projection repair and broader storage cost qualification remain open. The scheduler's operation/session/model-claim maps remain resident and still require lazy projections.

`open_task` recovers a task through the same registered definition without Rust input/output type parameters. `run_task` consumes an existing coordinator lease and a positive, bounded transition allowance. Its first trigger is null; later inputs are an owner-authorized wake value or ordered command results shaped as `{"commands":[{"operation_id":...,"value":...}]}`. A suspended checkpoint releases its reservation through the existing scheduler and retains no waiting future. `task_host().resume_workflow` requires the signed owner's `operation:wake` grant, the exact checkpoint revision, task-readable verified JSON and an explicit source-event retry key. The retained wake remains present across admission/crash and is consumed by advancing past its revision. A pending command may consume a wake without advancing its checkpoint and suspend again.

`poll_task_wake(task)` performs one owner-bound passive wake poll. The worker retains the exact pending command in the existing scheduler suspension slot, alongside the checkpoint revision. The poll verifies the workflow admission and reads one checkpoint plus the selected task-readable command body; it never dispatches model/tool work or acquires a reservation. A timer must already have its exact deadline retained and be due under the host clock; mail checks the first immutable inbox item and its actual task-readable file; child observation checks the derived direct child's settled outcome. When ready, the existing signed `operation:wake` path publishes verified JSON `null`. The worker reruns its ordered outbox under a newly admitted lease, rather than treating the readiness read as a command result.

Wake publication checks the selected command, suspension revision and uncancelled phase at the coordinator snapshot used by tail CAS. Logical wake identity includes the command because successive commands can wait at one checkpoint revision; physical retry identity also includes the coordinator tail to recover retained failed CAS receipts. Polling a consumed slot, an input-only/legacy suspension, or an unsupported passive command returns false. The caller can use `poll_task_wake_page(cursor, maximum_events)` to discover passive waits from verified coordinator events. The caller selects any positive event allowance; each internal page inspects at most the smaller of that allowance and 64 events in a fixed inclusive snapshot and retains at most that many distinct current owned candidates. Persist the serializable `TaskWakeCursor` between pages or restarts; it is a resume hint, not execution authority. A completed sweep returns no cursor. Begin another sweep later so waits that were not ready are reconsidered even when timer or inbox readiness produces no coordinator event. Wake appends cannot extend the current snapshot. Failed pages can reuse their input cursor; already filled slots are skipped. Foreign owners, cancelled tasks and legacy input-only waits are excluded before command polling. No background watcher, second queue or timer future is retained. Coordinator refresh still uses resident semantic maps; lazy projection and repeated full-sweep costs remain open.

`worker_tick(worker, cursor, commands, maximum_events, maximum_transitions)` composes one wake discovery page, at most one owner-scoped admission, and one existing registered worker turn. `CoordinatorTaskHost::pull_work` calls `DistributedCoordinator::pull_owned`: candidate admission and dependency rejection require signed `operation:declare` and `operation:observe` and are restricted to that owner, while capacity subtraction and publication use the same scheduler and coordinator tail. It adds no scheduling queue or accounting ledger. A claimed lease still requires exact retained-reservation verification before execution. Admission publication/observation errors return `WorkPull::Unresolved` with the exact attempted lease; this does not prove that admission committed. The legacy unscoped `pull` remains available with its error-only result.

A tick returns its wake cursor and an optional `TaskWorkerAttempt`. Carry the cursor into the next tick and repeat completed sweeps later. Preserve leases returned by `Yielded`, `Reconciling` or `Unresolved`; use `resume_task(lease, commands, maximum_transitions)` explicitly. Every resumption error returns the original attempt, and a fresh tick does not rediscover an already active lease. Pass the existing stock command adapter, including its model binding, or a trusted `TaskCommandHost`. Neither the driver nor an error proves provider quiescence, releases uncertain capacity, refunds accounting or retries a provider outside its journal. The source page and machine allowance are bounded, but resident coordinator refresh/ready enumeration and repeated sweep costs remain open.

`TaskCommandHost` is a trusted adapter, not a new command registry or effects ledger. It must route stable command identities through existing journaled providers and report `Pending` only when no uncertain dispatch is active. Callback errors and `Indeterminate` retain the reservation in `Reconciling`. Resuming reconciliation requires that same lease; no fresh pull or accounting refund occurs. A bounded yield also returns the still-owned lease. Acknowledging cancellation and provider quiescence remains the adapter's responsibility. Task grants and payload residency are checked before callbacks, and ownership is checked before and after them.

`runtime.commands()` supplies Rust stock command adapters for `acyclic.model.v1` and `acyclic.tool.v1`. Stage a `ModelTaskCommand` or `ToolTaskCommand` as the workflow command's immutable JSON payload. Model commands require an explicit `with_model` binding and use the mandatory stock executor and shared accounting. Tool commands select an exact name/revision from the runtime's existing registry and use `DurableToolRunner` with a task-owned execution journal. Both derive execution identity from the task and logical command identity; payloads cannot substitute it. Ready values serialize `Outcome<TurnOutput>` for models and `Outcome<Value>` for tools. An uncertain tool result returns `Indeterminate`, retaining the worker's reservation for reconciliation. These adapters introduce no additional registry, scheduler, or accounting ledger.

The composed harness binds its existing authenticated content reader, so tools can use `ToolContext::task().read_file` through retained task grants. The storage owner's broader access does not widen those grants. The restart regressions use actual file reads during tool execution and reconciliation, reject an unregistered pinned revision before dispatch, and verify one execution followed by one reconciliation after all runtime and store handles are reopened.

`acyclic.timer.v1` accepts a `TimerTaskCommand` with a positive absolute `deadline_unix_ms`. It requires the retained `timer:wait` grant and polls the existing task timer Stream, publishing the timer under the current lease and coordinator tail in one transaction. Exact retries retain the deadline; changing it conflicts. The legacy waiting API uses the same retained identity scan and a timer-tail comparison, so concurrent stock/legacy publications cannot duplicate the logical timer. Replay reads at most 64 records per page, retains only the selected timer match. History has no fixed lifetime ceiling; publication retries recheck ownership and retained identity without a fixed attempt count. Before the trusted clock reaches the deadline, the adapter returns `Pending` and the worker suspends without a sleeping future; when due, it returns serialized `Outcome::Succeeded(null)`. The owner-bound `poll_task_wake` can publish the existing authenticated wake when due; the caller drives polling and capacity admission. `open_with_clock` composes a trusted host clock, while `open` uses the system clock.

`acyclic.mail.send.v1` accepts a `MailSendTaskCommand` naming an admitted recipient and pinned payload file. It derives the message identity from the sending task and logical command, requires retained `mail:send`, and checks the recipient's file limits/read grants and actual payload residency. Publication uses the existing recipient mailbox and atomically compares the sender's current coordinator ownership and mailbox tail. Exact retries verify the retained event; changing sender or payload under that message identity conflicts. The legacy send API uses the same event scan and mailbox-tail comparison. Mail scans read at most 64 records per page, retain one selected identity match. Mailbox history and publication retries have no fixed ceilings; repeated scan costs still need qualification.

`acyclic.mail.receive.v1` accepts a `MailReceiveTaskCommand` with an exclusive one-based `after` cursor (zero starts the inbox). It requires retained `mail:read` and returns `Pending` if no item is committed. Otherwise it verifies the first item's file through the task's content reader and returns serialized `Outcome::Succeeded(InboxItem)`. It selects one immutable item rather than an append-sensitive partial batch, so later messages cannot change the command result during recovery before checkpoint publication. A send returns serialized `Outcome::Succeeded(null)`. The owner-bound `poll_task_wake` checks committed inbox readiness and publishes through the existing authenticated wake path; the caller drives polling and admission.

`acyclic.task.admit.v1` accepts a `TaskAdmitCommand` with an exact registered resumable task name/version and schema-checked input. It uses metadata from the same task registry, derives a child identity from the parent and logical command, and inherits the parent's retained grants and limits. The existing descendant grant and shared root ceilings apply. `admit_owned` uses the same admission validation/staging path and coordinator declaration, with a current uncancelled parent-lease check at the coordinator snapshot used by the declaration's tail CAS. Cached retries also check the parent lease. A refreshed tail gets a new physical Stream retry identity because failed CAS requests are retained, while the original logical declaration identity prevents another child or shared-budget charge. A successful command returns serialized `Outcome::Succeeded(TaskId)`.

`acyclic.task.observe.v1` accepts a `TaskObserveCommand` naming the logical operation of the prior admitting command. It resolves that command's derived direct child and returns its settled outcome. An absent result or indeterminate child execution returns `Pending`; the child retains its own execution ownership while the waiting parent releases its reservation. The owner-bound `poll_task_wake` publishes through the existing authenticated wake path when that child settles. These commands neither start another worker nor add a scheduler, registry or accounting ledger. Live tasks and required native extension runners are explicitly unsupported by this stock command composition.

Stock construction currently rejects routed execution and admitted execution deadlines whose runners are not composed; a timer command does not enforce that separate execution deadline. The local restart regressions cover checkpoint suspension/wake, durable child tasks/timers/mail and interrupted stock model/tool recovery with mandatory model accounting. Interaction and effect command adapters, deployment of the caller-driven page polling service, native extension dispatch, publication acknowledgement faults, lazy coordinator projections and final cross-platform qualification remain required. The stock command DTOs are currently a Rust Filesystem feature API; this checkpoint does not establish equivalent generated TypeScript/Wasm adapters.

Coordinator admission selects one candidate directly from the existing reducer rather than materializing every blocked/ready operation. Owner filtering happens before readiness checks. Capacity subtraction retains exactly the worker's advertised resource keys; omitted resources still have zero capacity, and partial admission checks only the missing quantity without copying the request. Shared session capacity uses the existing retained-reservation calculation. Full-list observation APIs still return complete lists. This removes transient selection lists and count maps, but resident coordinator maps, refresh, publication cloning and worst-case selection scans remain open bounds.

`FilesystemTaskRuntime::with_interaction_owner` installs that conversation verifier, schema registry, signed request-owner scope and private volume on the existing runtime providers. The scope must include `interaction:open`; response rights remain with the separately signed participant. Stock model journals use the binding when the admission includes `interaction:route`. Stock tool commands additionally bind their exact task context to the same leased journal through the existing `InteractionRouter` seam, reusing the host's task/operation ticket identity. A cloned context retains this exact journal fence; it cannot select another owner or bypass the task grant. Tasks without an interaction grant can still execute commands that need no approval. The durable-local policy regression retries one pending approval before provider dispatch, rejects resolution by the request owner, resolves with the ticket's exact responder grant, then drops all runtime/Filesystem/Stream handles and reconciles the approved tool once after reopening. It qualifies recovery of a resolved approval with an uncertain tool call. Confirmed pending approvals release the worker slot only after the execution-journal quiescence proof and atomic coordinator comparison. Passive readiness authenticates the retained command and exact approval without policy/model/tool callbacks. Real-store reopen controls cover typed and model-triggered approval, declined model approval without tool dispatch, cancelled waits without stale wake, and one tool dispatch followed by lost-result reconciliation. An uncertain tool execution retains its reservation. Broader provider acknowledgement faults and platform gates remain open. No protocol DTO changed.

Cold model-selection verification reads its committed operation and the selected message locators at that operation's event cutoff. Canonical checkpoint reconstruction reads the exact message-sequence range after the previous checkpoint coverage, including non-model messages before filtering the projection. These locators share the original message publication commit; missing, altered, or later records reject without a replay fallback. `FilesystemExecutionJournal::with_history_read_limits(HistoryReadLimits)` sets a separate positive message-work and encoded-byte allowance for those canonical range reads. Without an override, the admitted `Limits::context_messages` also caps the number of canonical records read, and the byte ceiling covers two maximum-sized protocol records per message. This read allowance does not expand model projection or content grants. It does not evict the conversation reducer's resident history.

The owner-proof coordinator uses history version 3. Its event stream, retry-location namespace and idempotency identity are separate from legacy version 2. Version-2 declarations lack the authenticated original owner grant and are not automatically migrated. Keep legacy histories with their matching reader; new version-3 operations require explicit original signed grants and fresh operation identities.
